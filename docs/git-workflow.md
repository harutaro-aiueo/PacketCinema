# ブランチ・PR運用

mainを確認済みの変更を集めるブランチとし、機能・教材追加、修正、文書更新は短期の作業ブランチで進めます。常設のdevelopは設けません。

## 日常の作業

1. 作業ツリーと現在のブランチを確認します。同じ依頼の作業ブランチは継続します。新しい作業ではremoteを確認してfetchし、最新のmainから `codex/<作業内容>` を作ります。取得できない場合は基点の未確認を報告します。既存変更を勝手にstash・破棄したり、無関係なコミットを含めたりしません。
2. 1ブランチ・1PRを1つの目的に絞って実装します。大きな追加では目的と完成条件をIssueに整理できますが、Issue作成を毎回必須にはしません。
3. AGENTS.mdと該当スキルに沿って検証します。文書だけならローカルでは内容・リンクを確認します。CIは検証漏れを防ぐため、文書のみを含むすべてのmain向けPRでテスト・build・E2Eを実行します。
4. commit・push・PR投稿が依頼された範囲で、送信内容を確認して作業ブランチをpushし、main向けPRを作ります。実装途中ならDraftにします。本文には変更の目的と結果、検証、未確認事項を記載します。
5. マージが依頼されている場合、最新差分と `PR validation` の成功を確認してSquash mergeします。一人開発でもPRの差分を確認します。他者の承認は必須にしません。
6. マージ済みブランチは次の作業に流用しません。削除は未送信の作業がないことを確認し、リモート削除は依頼または設定済みの自動削除の範囲で行います。公開は[公開手順](publishing.md)に従います。

これらの手順はcommit・push・投稿・マージ・公開の包括的な許可ではありません。会話ですでに認められた操作は再確認せず進めます。GitHubへの操作には利用可能なgithub-guardrailsスキルを適用します。

## GitHub側の初期設定

文書やスキルだけではmainへの直接pushを強制的に防げません。管理権限を持つ利用者が次を設定します。実設定の変更が依頼されている場合だけ適用し、文書更新だけで設定済みと扱いません。

- mainの保護ルールを有効にし、PR経由の変更と必須チェック `PR validation` の成功を要求します。厳密に確認するため、マージ前にmainの最新変更を取り込むことも要求します。
- 一人運用では承認レビュー人数の必須条件を設けません。mainのforce pushと削除は禁止し、通常の管理者操作にも保護を適用します。
- マージ方式はSquash mergeを有効にし、通常のmerge commitとrebase mergeを無効にします。必要ならマージ済みブランチの自動削除を有効にします。
- [PR用CI](../.github/workflows/ci.yml)を導入してPRで一度実行し、実際のチェック名を確認してから必須チェックに登録します。存在しないチェック名を必須にしません。必須チェック用のワークフローにはパス除外を付けません。
- Pagesは手動公開を維持します。PR用CIはデプロイせず、Pagesの必須チェックをPRに要求しません。

GitHub側の保護機能の利用可否はリポジトリの公開範囲とプランに依存します。設定できない場合もPR運用を守り、強制保護が未設定であることを報告します。
