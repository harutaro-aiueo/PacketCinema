# GitHub Pagesへの公開

公開設定の正本は[pages.yml](../.github/workflows/pages.yml)。現在は`workflow_dispatch`のみで起動するため、pushだけでは公開されません。作業時に設定を再確認してください。

[ブランチ・PR運用](git-workflow.md)に従い、通常の公開対象はPRをマージしたmainのコミットとします。

## 公開までの流れ

1. 依頼の範囲がcommit・push・PR作成・マージ・Pages公開のどこまでか確認します。会話ですでに指定されている場合はその範囲で進めます。この文書自体は公開の許可を与えません。
2. 現在のブランチ、送信先、差分、未追跡ファイルを確認します。GitHub操作には利用可能な`github-guardrails`スキルを適用し、送信内容と機密情報を確認します。`output/`や`debug.log`などのローカル確認用成果物は、公開対象として明示された場合を除き含めません。
3. アプリ変更は`npm test`、`npm run build`、`npm run test:e2e`で検証します。同じ差分について直前に成功した検証は再利用できます。文書だけの変更はリンクと内容を確認します。Pagesワークフロー内でも3コマンドが実行されます。
4. 作業ブランチで対象ファイルを明示してcommit・pushします。PR作成・マージが依頼範囲に含まれる場合、main向けPRの差分と最新のCI成功を確認してSquash mergeします。公開も依頼されている場合、マージ後のmainのSHAを記録し、GitHub Actionsの「Build and deploy Pages」をmainで実行します。作業ブランチのSHAとSquash merge後のSHAを混同しません。
5. 実行されたワークフローのコミットSHAが公開したいものと一致し、build・deployが成功したことを確認します。失敗時は原因を調べ、内容を変えずに繰り返し再実行しません。
6. ワークフローが返す公開URLで、変更した教材・表示を確認します。push成功、デプロイ成功、公開画面での確認を区別して報告します。

GitHub操作は`gh` CLIを優先します。PATHから解決できない場合も、OSの標準的なインストール先（WindowsではProgram FilesやユーザーのLocalAppDataなど）を確認し、見つかれば実行ファイルを直接指定します。`gh`が利用できないと確認できた場合にブラウザー操作へ切り替えます。認証情報や個人環境の実行パスをこの文書へ保存しません。
